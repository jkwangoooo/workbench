## 二、两个必须先处理的问题（不是新功能）

这两项不解决，后面加的页面越多、数据越不可挽回。

### 问题 1：全部数据只存在"这台电脑的这个浏览器"里

`localStorage` 没有任何导出/备份入口。清缓存、换浏览器、重装系统、换电脑 —— 一个学期的违纪、作业、成绩、听写记录**全部消失且无法恢复**。这比缺任何一个页面都严重，而且它本身就是一个纯本地功能。

### 问题 2：学生 ID 是按序号派生的，顺序一变历史记录就错位

`app/core/roster.js` 里 `id: local-8-${index + 1}` —— ID 由**种子文件里的排序**决定。而所有历史数据都以这个 ID 为外键：

- 作业反馈 `data['8:2026-09-14'][studentId]`
- 单元测试 `test.scores[studentId]`
- 听写成绩 `sheet.scores[studentId:columnId]`
- 目标分 `sheet.targets[studentId]`

只要有人往 `private-data/students.js` 里插一名学生、调一次顺序，**全班的历史成绩都会静默错位到隔壁同学名下**，而且不会有任何报错。这是静默数据污染，必须在上真实数据之前修掉。

### L0 · 数据安全网（已完成）

| 编号 | 任务 | 交付物 |
| --- | --- | --- |
| L0-1 | 一键导出全量备份（单个 JSON，含 `app` / `schema` / `exportedAt` / `roster` / 白名单内的全部数据） | `app/pages/data.js` 的「导出全部数据」；白名单是 `app/core/constants.js` 的 `EXPORT_KEYS` |
| L0-2 | 导入备份并恢复：先解析、显示记录条数与导出时间、核对名单指纹，二次确认后才覆盖 | 同页「恢复备份」面板 |
| L0-3 | 学生 ID 稳定化：由稳定键派生，与种子里的排列顺序无关 | `app/core/student-id.js` + `app/core/roster.js` 改造 |
| L0-4 | 旧数据迁移：把 `local-8-*` 旧 ID 映射到稳定 ID，只跑一次并留痕 | `app/domain/migrate.js` |

**验收**：在一个全新的浏览器里，仅靠导出的 JSON 就能完整恢复全部记录；改动种子文件的顺序后，历史成绩仍挂在正确的学生名下。

**实际验收结果**（均已通过）：

- `npm test` —— 32 项，其中新增 `local-app-id`（6 项）、`local-app-backup`（11 项）。
- `npm run verify:local` —— 真机 16 项，走通「记待办 → 导出 → 清空浏览器存储 → 恢复 → 刷新仍在」闭环，另含旧 ID 自动迁移与幂等、桌面/手机视口无横向溢出、控制台无 error/warning。

**与计划的偏差**：L0-3 最终没有采用「姓名 + 学籍号」拼接，而是对稳定键（优先省学籍辅号 / 准考证号 / 证件号，都没有才退回姓名）做 **FNV-1a 32 位哈希**。理由是拼接会把真实学籍号原样写进 `localStorage` 和备份文件，而哈希与排列顺序无关、不泄露原件，重名学生再按序补 `-2` 后缀区分。

## 四、每个新功能必须遵守的约束（为将来上云铺路）

即使本轮不碰云端，也按这些约束写，之后迁云不用重写业务逻辑：

1. **纯本地可运行**：不发起任何网络请求；功能不依赖账号、不依赖云端可用性。
2. **实体带完整身份**：新记录一律带 `id`（用 `uid()`）、`createdAt`、`updatedAt`，方便将来与云端行对齐。
3. **键必须登记**：新增 `localStorage` 键必须写进 `app/core/constants.js` 的 `LOCAL_KEYS`，并加入导出白名单，否则备份会漏数据。
4. **新页面三处登记**：`app/pages/<name>.js`、`app/main.js` 的路由、`app/ui/shell.js` 的导航与标题表。
5. **依赖方向不破**：`core` → `domain`/`io` → `pages` → `ui` → `main`，`npm run check` 会拦。
6. **每个阶段补测试**：纯逻辑进 `tests/unit/local-app-domain.test.mjs`；页面渲染进 `tests/unit/local-app-render.test.mjs`。
7. **改完跑门禁**：`npm run check`，截图验收后再提交。

## 六、建议的推进节奏

用户按页面逐个提出优化，每一轮走同一条流水线：

```
选页面 → 我读该页源码 + 对应需求文档 → 给出改动方案（含影响面）
→ 实现 → 补/改测试 → npm run check → 起服务截图验收 → 提交
```

第一个建议从 **L0** 开始（不是因为它是新功能，而是因为它是唯一"拖得越久越可能造成不可挽回损失"的一项）。
